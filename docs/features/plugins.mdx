Plugins are the third Resource Kind in Skillset. Where a Skill is a single `SKILL.md` bundle, a Plugin is a multi-resource bundle for an agent to load together — a repository containing a `.claude-plugin/plugin.json` manifest plus any combination of `skills/`, `commands/`, `agents/`, `hooks/`, and `.mcp.json`. This page covers the Plugin structure, how it differs from a Skill, and the publish and install workflow.

## What is a Plugin?

A Plugin bundles everything an agent needs for a particular workflow or integration: Skills, slash commands, sub-agents, lifecycle hooks, and MCP server configurations can all live together in one repository. The Registry stores the Plugin's files as an Artifact and serves them on demand, exactly as it does for Skills.

**The Registry never inspects a Plugin's contents.** The Skills a Plugin contains are its own business — they are not individual rows in the Registry and do not appear separately in the catalog. This is a deliberate design choice (ADR-0001): the Registry validates the manifest's presence and the Artifact's size and path rules, nothing more.

<Note>
  A Plugin's internal Skills are not installable or searchable separately through Skillset. If you want individual Skills discoverable in the catalog, publish them as Skill resources alongside the Plugin.
</Note>

## Repository layout

A Plugin repository must contain `.claude-plugin/plugin.json` at its root. The rest of the layout is flexible, but the conventional structure is:

```
my-plugin/
├── .claude-plugin/
│   └── plugin.json        ← required manifest
├── skills/
│   └── code-review.md
├── commands/
│   └── review.md
├── agents/
│   └── reviewer.md
├── hooks/
│   └── pre-commit.md
└── .mcp.json              ← optional MCP server config
```

### plugin.json manifest

The `.claude-plugin/plugin.json` manifest is the only file the Registry requires at a specific path. Its schema is defined by the Claude plugin specification. The Registry stores it as part of the Artifact without parsing its contents.

```json
{
  "name": "code-review-suite",
  "description": "A complete code review toolkit with skills, commands, and hooks.",
  "version": "1.0.0"
}
```

## How Plugins differ from Skills

<CardGroup cols={2}>
  <Card title="Skill" icon="file-lines">
    A single `SKILL.md` bundle with optional supporting files. The `SKILL.md` frontmatter is the source of truth for `name` and `description`. Individually searchable and installable.
  </Card>
  <Card title="Plugin" icon="layer-group">
    A multi-resource bundle behind a `.claude-plugin/plugin.json` manifest. May contain Skills, commands, agents, hooks, and MCP configs. The internal contents are opaque to the Registry.
  </Card>
</CardGroup>

| | Skill | Plugin |
|---|---|---|
| Root manifest file | `SKILL.md` | `.claude-plugin/plugin.json` |
| Registry inspects contents | Frontmatter only | Never |
| Internal resources as catalog rows | N/A | No |
| Appears in Marketplace | Yes | Yes |
| Has Artifact | Yes | Yes |
| Import from Git | Yes | Yes |

## Publishing a Plugin

Publish a Plugin by uploading its folder in the web interface, or with the CLI's `publish` command from a local directory. The same Artifact limits apply as for Skills (1,000 files, 25 MB uncompressed, 10 MB compressed).

```bash
# Publish the Plugin in the current directory
skillset publish

# Publish from an explicit path
skillset publish ./my-plugin
```

The CLI publishes a directory as a `plugin` when its root holds `.claude-plugin/plugin.json`, and as a `skill` when its root holds `SKILL.md`. The Plugin's name, description, version, license and homepage come from the manifest. Publishing the same name again replaces the Plugin.

<Warning>
  A directory that contains both `SKILL.md` and `.claude-plugin/plugin.json` will be rejected as ambiguous. Use a separate directory for each Resource.
</Warning>

<Note>
  A Plugin is published from a folder on disk. Publishing straight from a GitHub or GitLab URL takes Skills only, for now.
</Note>

## Supported agents

A Plugin supports an agent when it holds that agent's manifest. The Registry reads this from the folders present and shows them as the Plugin's **Agents**, with one install tab each.

| Folder | Agent |
|---|---|
| `.claude-plugin/plugin.json` | Claude Code |
| `.cursor-plugin/plugin.json` | Cursor |
| `.codex-plugin/plugin.json` | Codex |

A Plugin can hold several. Every manifest must give the same `name`. A Plugin is never offered for an agent it has no manifest for, even one that could load another agent's format.

## Installing a Plugin

```bash
# Install for the only agent the Plugin supports, or pick from the ones it does
skillset plugins install code-review-suite

# Install for one agent
skillset plugins install code-review-suite --agent cursor
```

Each agent installs differently:

- **Claude Code:** the CLI adds this Registry's marketplace (`claude plugin marketplace add <registry>/.claude-plugin/marketplace.json`) and runs `claude plugin install <name>@skillset`. Claude Code then downloads the Plugin and keeps it up to date. The Registry must be served over HTTPS on a non-loopback host: Claude Code refuses plugin archives from anywhere else.
- **Cursor:** the CLI downloads the Plugin and copies it to `~/.cursor/plugins/local/<name>/`. Restart Cursor, or run "Developer: Reload Window", to load it.
- **Codex:** the CLI downloads the Plugin into a local Skillset marketplace at `~/.agents/plugins/local/skillset/`, adds that marketplace to Codex, and runs `codex plugin add <name>@skillset`.

A Plugin's page has an Installation panel with a dropdown of the agents it supports. Each one shows the `skillset plugins install` command for that agent, ready to copy.

Run the command again to update a Plugin installed for Cursor or Codex. Claude Code and Codex need their own CLIs (`claude`, `codex`) on your `PATH`.

## Marketplace

The Registry serves a Claude Code marketplace at `/.claude-plugin/marketplace.json`. It lists every Plugin that supports Claude Code, as entries with `archive` sources, so Claude Code can install from it without the `skillset` CLI:

```bash
claude plugin marketplace add https://skills.example.com/.claude-plugin/marketplace.json
claude plugin install code-review-suite@skillset
```

Cursor and Codex cannot read a marketplace from a URL, so the Registry serves none for them; `skillset plugins install` is how they install. MCP Servers are never listed, because the Registry has no bytes to point at for them.

## Tags

Plugins use the same Tag catalog as Skills and MCP Servers. Writers attach Tags via the web interface or `PUT /api/resources/{id}/tags`. Tag filtering works identically across all Kinds.

```bash
# Search for Plugins with a specific tag
GET /api/resources?kind=plugin&tag_id=<id>
```
